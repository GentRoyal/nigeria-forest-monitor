# API access and local exports

The API is interactive-session first. Organisation owners and administrators can
create machine credentials with `POST /api/v1/api-keys`. The returned `secret`
is shown exactly once; store it in a secret manager, never in source control.

API keys are sent as `X-API-Key` and have additive scopes:

- `read` permits safe `GET` and `HEAD` requests.
- `write` permits non-export state changes, subject to the accountable user's role
  and normal site visibility rules.
- `export` permits `POST /api/v1/exports`, again subject to the accountable user's
  role and site visibility rules.

API keys cannot create, list, or revoke other API keys, and never bypass the
accountable user's permissions. Revoke a key with
`DELETE /api/v1/api-keys/{key_id}`. `GET /api/v1/admin/usage` provides the local
workspace usage projection for an owner or administrator.

Example machine read request:

```powershell
$headers = @{ 'X-API-Key' = $env:NFM_API_KEY }
Invoke-RestMethod http://localhost:8000/api/v1/sites -Headers $headers
```

Exports are generated by the parameterised Airflow DAG `nfm_export_generator`.
After an export reports `completed`, call `POST /api/v1/exports/{export_id}/download`
to obtain its short-lived local content reference, then request that reference with
the same authenticated identity. The API verifies that the generated file remains
inside `NFM_EXPORT_ROOT`; the worker's completion callback also verifies the file
and SHA-256 checksum before marking an export complete.

This local-file flow is deliberately replaceable: production deployment should use
private object storage and signed URLs instead of a shared Docker volume.

Derived assets are served through the equivalent authenticated
`GET /api/v1/assets/{asset_id}/content` flow. Local files must be placed below
`NFM_ASSET_ROOT` (mapped to `data/assets` in Docker Compose); path traversal and
missing files are rejected before a reference or file is returned.
